Learn Claude Code

From your very first command to advanced power-user workflows — an interactive guide for every level. No prior experience needed.

What is Claude Code?

Claude Code is Anthropic's official CLI that puts Claude directly in your terminal. Unlike the web chat, it can read and write your files, run commands, search your codebase, and work on multiple tasks in parallel — all without leaving your editor workflow.

New here? Click Beginner in the top-right toggle. The page hides advanced topics and shows only what you need for your first sessions. You can always reveal more by clicking "Show" on any collapsed section.

2. Login 
claude login

Getting Started

Your first 5 minutes

Do this now. Nothing to read first — just follow the steps.

  1. Open a terminal and go to any project folder:
    cd my-project
  2. Start Claude Code:
    claude
  3. Ask it something simple:
    What does this project do?
  4. Generate a memory file so Claude always knows your project:
    /init
  5. Type /help to see all available commands. Done.
Worried about safety? Add --permission-mode plan when starting. Claude will show you the full plan and wait for your approval before making any changes. 
claude --permission-mode plan

What happens when you run a command

Claude will sometimes ask permission before acting — for example, before editing a file or running a shell command:

Claude wants to run: Bash(npm test)
Allow? [y]es / [n]o / [A]lways / [N]ever
  • y — allow this one time
  • A — always allow this type of action for the rest of the session
  • n — deny once (Claude tries a different approach)
  • N — deny and don't ask again this session

Three things to know

  • Prompts — plain English instructions. Be specific: "fix the login bug in @src/auth.ts" works better than "fix the bug".
  • Tools — Claude's abilities: read files, edit files, run commands, browse URLs. You control which ones it can use.
  • Context — Claude's session memory. Think of it as a notepad that fills up over time. When it gets too full, use /compact to summarise it, or /clear to start fresh. Claude charges by how much text it processes, so keeping context lean saves money.

The Three Pillars

Three concepts explain everything Claude Code does. Once these click, the rest of the guide is just detail.

1. Prompts

What you type. Plain English works. The more specific, the better.

Weak: "Fix this"
Strong: "Fix the null error in @src/auth.ts line 42 without changing the function signature"

2. Tools

What Claude can do: read files, edit files, run terminal commands, fetch web pages. You approve each one — either once or for the whole session. Tools are what make Claude Code more powerful than the web chat.

3. Modes

How much Claude does before asking you. Default asks before each action. Plan shows you the whole plan first. Auto-accept edits files silently. See the next section — Modes is the most important thing to understand as a beginner.

The Three Pillars — prompts, tools, modes: the mental model behind everything.

Modes

Modes control how Claude handles permissions. You can change mode at any time — mid-session, per-project, or globally.

The four modes

Mode Behaviour Best for
Default Asks before each tool call. Safest. General use, unfamiliar codebases
Plan Claude proposes the full plan first; nothing runs until you approve. Complex tasks, infrastructure, anything irreversible
Auto-accept Edits File edits run silently; only destructive or network actions ask. Rapid prototyping, trusted codebases
Auto Claude auto-decides on routine low-risk actions; asks for anything risky. High-velocity development with some guardrails
Don't Ask Minimal prompts — accepts most actions silently. Scripted or headless use where you need fewer interruptions
Bypass Permissions No prompts at all. Requires --dangerously-skip-permissions flag. Sandboxed CI/CD environments only

How to switch modes

Keyboard shortcut (fastest)

Press ShiftTab inside a session to cycle through modes. The current mode is shown in the status line.

CLI flag (per-session)

claude --permission-mode plan           # start in plan mode
claude --permission-mode acceptEdits   # start with auto-accept edits

settings.json (persist as default)

# ~/.claude/settings.json
{
  "defaultMode": "plan"
}

Plan mode in depth

Plan mode is the single highest-leverage habit for new users. When active:

  1. Claude analyses your request fully.
  2. It writes out a step-by-step plan of what it intends to do.
  3. You review the plan. Edit it, reject it, or approve with Enter.
  4. Claude executes the plan step by step. Individual tool calls may still ask for permission depending on your settings — plan mode controls when Claude starts, not whether each step is automatic.
When to use plan mode Any task where a mistake would be hard to reverse: migrations, deletions, deploy scripts, large refactors, or anything touching shared infrastructure.

Auto-accept Edits mode

Claude edits your files without asking, but still asks before running shell commands or making network requests. Good for fast iteration once you trust the direction. You can always Esc to interrupt and use /rewind to undo changes.

Bypass mode ⚠

Skips all permission checks. Only use this when Claude Code is running inside a Docker container, CI job, or other sandbox where it literally cannot reach anything sensitive.

claude --dangerously-skip-permissions -p "run the test suite"
Warning Never run bypass mode on your local machine against a real codebase or credentials.

CLAUDE.md & Memory

CLAUDE.md is a Markdown file that Claude reads automatically at the start of every session. It's your persistent prompt — the place to put everything Claude should always know about your project.

The three memory files

FileScopeBest for
.claude/CLAUDE.md This project Architecture, conventions, commands, do/don't rules for this repo
~/.claude/CLAUDE.md All your projects Personal style preferences, global rules, preferred libraries
Enterprise CLAUDE.md Whole org (managed) Company security policies, approved tooling, naming standards

What to put in CLAUDE.md

# My Project

## Architecture
- Backend: Node 20 + Express
- Frontend: React + TypeScript (strict mode)
- Database: PostgreSQL via Prisma

## Coding standards
- 2-space indentation
- Prefer `const` over `let`
- All async functions must have explicit error handling
- No `any` types

## Key commands
- `npm run dev` — start dev server
- `npm test` — run Jest tests
- `npm run db:migrate` — run Prisma migrations

## Important
- Never commit .env files
- The /api/auth route is read-only — don't modify it

Session memory: the # prefix

To add a temporary note just for this session, prefix your message with #:

# The auth module uses JWT, not sessions — don't add cookie logic

Claude will remember this for the rest of the session. It's forgotten on /clear or session exit — it doesn't write to any file.

The /memory command

Type /memory in a session to view and edit the CLAUDE.md files that are currently loaded. Useful for checking what Claude actually knows at any point.

Tip If Claude keeps making the same mistake, add a rule to CLAUDE.md. It's faster than re-explaining every session.

Context Hygiene

Think of each Claude session as a limited notepad. As the conversation grows, that notepad fills up — making responses slower, more expensive (Claude charges by the amount of text it processes), and eventually less accurate. Keeping it lean is one of the highest-leverage habits.

/clear vs /compact vs /resume

CommandWhat it doesWhen to use
/clear Wipes the entire conversation. Fresh start. Switching to a completely unrelated task
/compact Summarises the conversation to a compressed form, preserving the key decisions and context. Long session, same task — want to continue without losing thread
/resume Opens a prior session (by date/name). Context is restored from where you left off. Coming back to yesterday's work

Signs your context is "poisoned"

  • Claude keeps referencing a decision you changed 10 messages ago.
  • It contradicts itself on a simple fact.
  • It's giving longer and vaguer answers than usual.
  • It starts hallucinating file contents you know are wrong.

When you see these: /compact first (preserves continuity), then /clear if that doesn't help.

Cost awareness: @file beats pasting

Pasting a 500-line file into every message is expensive — it fills the context quickly. Instead, reference it by path:

@src/auth.ts fix the JWT expiry bug

Claude reads the file via the Read tool — so the content is in the session once, not copied into your message text. The saving is that you don't bloat your message with raw code on every turn. Check the current session cost with /cost.

Rule of thumb Use /compact when you want to keep working on the same thing. Use /clear when you're done and starting something new.

The Five Extension Types

Five different ways to extend Claude Code. They all make Claude do more — but each one is for a different job. If you're ever unsure which to reach for, this table is the answer:

Type What it is How you invoke it When to reach for it
Slash command Built-in Claude Code capability (e.g. /clear, /compact) Type /name in session Session control, navigation, built-in workflows
Skill A reusable prompt packaged in a SKILL.md file you or a plugin provides Type /skill-name in session You run the same complex prompt 3+ times — package it once
Subagent A separate Claude instance that runs in parallel or in isolation Ask Claude to "use the Explore agent" or dispatch via Agent tool Heavy read-only investigation; parallel independent work; isolated context
MCP server An external process that exposes custom tools Claude can call (Jira, Slack, your API…) claude mcp add … then tools appear automatically You need Claude to interact with an external system or data source
Hook A shell script that runs automatically on a lifecycle event (before a tool, after a tool, on session start…) Configure in settings.json — runs automatically Automation, logging, enforcement, injecting context silently
Quick decision rule /command for built-in session control → skill for your own reusable prompt → subagent for isolated/parallel work → MCP for external tools and APIs → hook for silent background automation.

Sections 10–13 go deep on each. Or try the "Which tool for the job?" quiz at the bottom of the page.

Subagents

A subagent is like opening a second Claude in another tab — it works independently so your main conversation stays focused. Subagents can run in parallel, use restricted tools, or work in complete isolation. This keeps your main session's memory clean while heavy work happens elsewhere.

Built-in agent types

TypeTools availableBest for
general-purpose All tools Any isolated task you'd give the main agent
Explore Read-only (no Edit/Write/Bash) Investigating a codebase without touching files
Plan Read-only + planning Designing an approach without implementing it

How to spawn a subagent

Just describe the work in natural language:

Use the Explore agent to investigate how authentication is implemented
in this codebase. I'll work on the UI while you do that.

Or dispatch multiple in parallel:

Spawn two agents in parallel:
1. Explore agent: find all places that call the /api/users endpoint
2. Plan agent: design the schema migration for the new user roles feature

Custom agent definitions

Create a file at .claude/agents/my-agent.md or ~/.claude/agents/my-agent.md:

---
name: security-reviewer
description: Reviews code changes for OWASP vulnerabilities and auth issues
tools: Read, Bash
model: opus
color: red
---

You are a security expert reviewing code for vulnerabilities.
Focus on: injection, auth bypass, secrets in code, and OWASP Top 10.
Be terse. List issues with severity (critical/high/medium/low).

Then invoke it: "Use the security-reviewer agent on this PR diff."

When to use subagents

  • Heavy read-only investigation — Explore agent doesn't pollute your main context
  • Parallel independent work — multiple tasks that don't depend on each other
  • Isolated context — agent works on one thing; you work on another
  • Specialised personas — security reviewer, test writer, documentation agent
Rule Don't spawn subagents for simple sequential work. A single agent with a good plan is faster. Use subagents when you'd otherwise be blocked waiting.
Subagents — parallel Claude instances for isolated or concurrent work.

Skills & Plugins

What is a skill?

A skill is a packaged, reusable prompt. When you invoke /skill-name, Claude loads the skill's instructions and executes them — exactly as if you'd typed out the prompt yourself, but without having to remember it.

Creating your own skill

Create ~/.claude/skills/my-skill.md:

---
name: my-skill
description: One-line summary shown in autocomplete
---

<what-to-do>
Your full prompt instructions here.
</what-to-do>

Then invoke it with /my-skill in any session. Tab-completion suggests it automatically.

Where skills live

  • ~/.claude/skills/ — your personal skills, all sessions
  • .claude/skills/ — project-scoped skills, this repo only
  • ~/.claude/plugins/*/skills/ — skills shipped with plugins

Plugins: skills + more

A plugin bundles multiple skills, custom agents, MCP servers, and commands into a single installable unit.

# Install a plugin
claude plugin install plugin-name@marketplace

# List installed plugins
claude plugin list

# Discover new plugins
# Type /plugin > Discover in a session

Plugin structure

my-plugin/
├── .claude-plugin/plugin.json   # metadata
├── .mcp.json                    # MCP servers (optional)
├── agents/                      # custom agents (optional)
├── skills/                      # skills (optional)
└── README.md
Tip If you find yourself writing the same complex prompt repeatedly, turn it into a skill. Three repetitions = write the skill.
Skills & Plugins — packageable prompts you invoke with /skill-name.

MCP Servers

MCP (Model Context Protocol) lets you plug Claude into external apps — your Jira, Slack, internal database, or any API. Think of it as installing extensions. A small server process runs alongside Claude and exposes new tools; once connected, Claude can call them in any prompt, naturally, like any built-in capability.

Adding an MCP server

# Add a local (stdio) server
claude mcp add my-server -- npx my-mcp-package

# Add an HTTP server
claude mcp add figma https://mcp.figma.com/mcp

# Add with environment variables
claude mcp add my-server -e API_KEY=your-key -- npx my-mcp-package

# List all servers
claude mcp list

# Remove a server
claude mcp remove my-server

Project-scoped config (.mcp.json)

For servers that should be available to everyone on your team, commit a .mcp.json to the project root:

{
  "mcpServers": {
    "my-server": {
      "type": "stdio",
      "command": "node",
      "args": ["./tools/mcp-server.js"]
    }
  }
}

Transport types

TypeUse when
stdioLocal binary on the same machine (most common)
httpRemote server over HTTPS
sseStateful remote connection (Server-Sent Events)
Security Only add MCP servers from sources you trust. An MCP server has the same tool access you've granted Claude. A malicious server could exfiltrate context.
MCP Servers — connect Claude to external tools (Jira, Slack, custom APIs).

Hooks & settings.json

Settings hierarchy

Settings cascade in this order — later entries override earlier ones:

  1. Enterprise defaults (org-managed)
  2. ~/.claude/settings.json — your user settings
  3. .claude/settings.json — project settings (commit this)
  4. .claude/settings.local.json — local overrides (gitignore this)
  5. CLI flags on the current session

Key settings fields

// ~/.claude/settings.json
{
  "model": "claude-sonnet-4-6",
  "defaultMode": "plan",
  "effortLevel": "high",
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm *)", "Read(**)", "Edit(**)"],
    "deny":  ["Bash(rm -rf *)"],
    "ask":   ["Bash(curl *)", "WebFetch(*)"]
  },
  "env": {
    "NODE_ENV": "development"
  }
}

Hooks

Hooks run shell commands automatically on lifecycle events:

EventFires when
PreToolUseBefore any tool runs
PostToolUseAfter a tool succeeds
PostToolUseFailureAfter a tool fails
UserPromptSubmitWhen you submit a prompt
SessionStartWhen a session begins
SessionEndWhen a session ends
StopWhen you press Esc
SubagentStopWhen a subagent finishes

Example 1: log every bash command Claude runs

// ~/.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "echo \"$(date): $CLAUDE_TOOL_INPUT\" >> ~/claude-bash.log"
        }]
      }
    ]
  }
}

The hook receives tool information via environment variables (CLAUDE_TOOL_INPUT, CLAUDE_TOOL_OUTPUT, etc.) and can log, validate, or block based on them. A non-zero exit code from the hook blocks the tool call.

Example 2: inject current git branch into every prompt

// ~/.claude/settings.json — UserPromptSubmit hook
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "matcher": "",
        "hooks": [{
          "type": "command",
          "command": "echo \"Current branch: $(git branch --show-current 2>/dev/null || echo 'not a git repo')\""
        }]
      }
    ]
  }
}

Text written to stdout by a UserPromptSubmit hook is prepended to the user's prompt as context — so Claude automatically knows the current branch without you typing it.

Note Hook environment variables and exact stdin/stdout behaviour may vary across Claude Code versions. Check claude --help or the official docs for the current spec before building complex hooks.
Hooks & settings.json — automate events, configure permissions, inject context.

Working in Parallel

The "3–4 terminal tabs" pattern you've seen online is real, but most people using it are doing it wrong. Here's the exact model and when to use it.

First: do you actually need multiple tabs?

A single Claude session dispatching parallel subagents is correct most of the time. You only need multiple terminal tabs when:

  • Human attention is split — you want to review/steer one task while another runs
  • Branches diverge — you're working on two features that shouldn't share file state
  • Long-running background tasks — a test suite, a build, or a migration that shouldn't block your foreground session

The anti-pattern: 4 tabs on the same files

Anti-pattern Four Claude sessions all editing overlapping files = merge conflicts, lost changes, and inconsistent context. Don't do this.

The correct pattern: git worktrees

Each tab works in its own git worktree — a separate checkout of the repo on a separate branch. File changes are isolated. Claude sessions have separate .claude/ state.

# Main checkout — feature A
cd ~/projects/my-app          # Tab 1: claude here

# Create worktree for feature B on its own branch
git worktree add ../my-app-feat-b feat-b-branch
cd ../my-app-feat-b           # Tab 2: claude here

# Both run in parallel with no file conflicts

The canonical 3-tab pattern

╔══════════════════════════════════════════════════════════════╗ ║ CANONICAL MULTI-TAB WORKFLOW ║ ╠══════════════════════════════════════════════════════════════╣ ║ ║ ║ TAB 1 — Driver (main checkout) ║ ║ • Plan mode ║ ║ • Review output from other tabs ║ ║ • Steer direction, approve plans ║ ║ ║ ║ TAB 2 — Implementer (git worktree, feature branch) ║ ║ • Auto-accept edits mode ║ ║ • Executes the plan from Tab 1 ║ ║ • File changes isolated to this worktree ║ ║ ║ ║ TAB 3 — Reviewer / Tester (same or separate worktree) ║ ║ • Default or plan mode ║ ║ • Runs tests, reviews diffs, /review skill ║ ║ • Reports back to Tab 1 for next steps ║ ║ ║ ║ TAB 4 — Background research (optional) ║ ║ • Explore agent dispatched from Tab 1 ║ ║ • Or: `claude -p "..."` for a one-shot ║ ║ • Long-running; Tab 1 continues while it works ║ ║ ║ ╚══════════════════════════════════════════════════════════════╝

Session commands for multi-tab work

# Resume a prior session by name
claude --resume "feature-b-implementation"

# Name the current session for easy resumption
# (set in --name flag or the session shows in /resume list)

# View all running/background sessions
claude agents

# Run a one-shot in the background and pipe to file
claude -p "summarise open PRs" --output-format json > pr-summary.json &
Simpler alternative For most tasks, claude in one tab + "spawn two parallel agents" in your prompt is faster and less error-prone than managing multiple tabs manually.

Workflows

Four end-to-end recipes — each with the exact commands and prompts in order.

W1. Starting a new project from zero

Also works for onboarding onto a legacy codebase — just lean harder on /init.

cd my-project
claude

# Step 1: Let Claude understand the project
/init
# Claude generates .claude/CLAUDE.md — review and edit it

# Step 2: Switch to plan mode for the first feature
claude --permission-mode plan
# or press Shift+Tab until "plan" shows

# Step 3: Describe what you want
Implement user authentication with JWT.
Use the existing Express setup in src/server.ts.
Follow the conventions in CLAUDE.md.

# Claude writes the plan. Review, approve, done.

W2. Investigating and fixing a bug

# Step 1: Spawn an Explore agent to reproduce the bug in isolation
Use the Explore agent to investigate the bug in the checkout flow.
Reproduce the error and find the root cause. Don't edit anything.

# Step 2: While Explore runs, continue in the main session
# (or switch to plan mode and design the fix)

# Step 3: Apply the fix
Apply the fix the Explore agent found. Use plan mode.
Run the tests after.

# Step 4: Verify
!npm test

W3. Resuming a long-running task across days

# Day 1: End of session — add a handoff note
# Before closing: we finished the schema migration.
# Next: update the API endpoints to use the new user_roles table.
# Blocked on: need to confirm the JOIN behaviour with @src/db/queries.ts

/compact Keep the schema migration notes and the TODO above

# Day 2: Resume
claude --resume    # pick the session from the list

# Or if you named it:
claude --resume "user-roles-migration"

# Your compacted context + the handoff note are there
# Continue exactly where you left off

W4. Headless / CI use

# One-shot: no interactive session
claude -p "Review this diff for security issues" \
  --output-format json \
  --permission-mode bypassPermissions \
  > security-report.json

# Stream results in real time
claude -p "Run tests and summarise failures" \
  --output-format stream-json \
  --include-partial-messages

# In a Makefile or CI step
review:
    claude -p "Review changed files in this PR" \
      --add-dir src \
      --model sonnet \
      --output-format json > .ci/review.json

Debugging Claude Code Itself

When Claude Code itself is misbehaving — not the code it writes, but the tool itself.

Diagnostic checklist

SymptomTry this first
Authentication errors /doctor → then claude login
Tool calls failing silently claude -d --debug for verbose logs
Responses getting worse over time /compact then /clear — context poisoning
Claude is looping or stuck Esc to interrupt → restart with a smaller, more specific task
Wrong file being edited Check .claude/CLAUDE.md — likely a stale instruction pointing to old paths
Permissions prompt every time Add patterns to settings.json permissions.allow
Claude Code crashes or won't start claude doctor from the terminal (outside a session)
Responses hallucinating file contents Use @filepath to make Claude re-read the actual current file

When to switch models

Different models have different strengths:

  • Opus — best reasoning, slowest, most expensive. Use for architecture decisions, complex debugging.
  • Sonnet — best balance. Use for most development tasks.
  • Haiku — fastest, cheapest. Use for simple lookups, quick formatting, batch headless tasks.

Switch mid-session: /model sonnet

Filing a bug

If you've found a genuine Claude Code bug (not model quality, but the tool itself): type /bug in a session to open a pre-filled GitHub issue with your version and context automatically included.

Prompting Cheatsheet

Claude Code–specific habits. Each one saves tokens, time, or frustration.

New? Start with these 5 Items 1, 3, 4, 6, and 12 are the highest leverage for beginners. The rest are for when you're comfortable.
  1. Use @file instead of pasting code. @src/auth.ts fix the bug is far cheaper than pasting 500 lines. Claude reads the file directly — you don't bloat your message with raw code on every turn.
  2. Use # to teach Claude mid-session. Type # The auth module uses JWT, not sessions — Claude remembers it for the rest of the session. For permanent rules, put them in CLAUDE.md instead.
  3. Use plan mode when scope is unclear. If you're not sure what needs to change, start in plan mode. Reviewing a plan costs nothing; undoing a wrong implementation does.
  4. /clear between unrelated tasks. Don't carry context from "add dark mode" into "fix the auth bug". Each task deserves a fresh session.
  5. /compact instead of /clear when continuing. Same task, session getting slow? Compact summarises the conversation and keeps the thread. /clear loses everything.
  6. Put your rules in CLAUDE.md, not every prompt. "Always use TypeScript strict mode" belongs in .claude/CLAUDE.md. It loads automatically every session — you never type it again.
  7. Use the Explore subagent for investigations. "Use the Explore agent to find all usages of this function" — the agent works read-only in isolation, keeping your main session's memory clean.
  8. Never paste secrets into a prompt. Don't paste API keys or passwords. Reference the file instead: Use the credentials in .env to test the connection.
  9. Use claude -p for repeatable tasks. Anything you'd run the same way twice should be a shell script or CI step: claude -p "review this diff" --output-format json. Not a manual session each time.
  10. Use --tools "" for a read-only advisor session. claude --tools "" gives Claude zero tool access — pure conversation. Useful for discussing architecture without any risk of file changes.
  11. Check /cost on long sessions. High cost usually means you're carrying too much context. Compact or restart. Haiku is 10–20× cheaper than Opus for simple tasks — switch with /model haiku.
  12. Esc Esc to fix your last prompt. Spotted a typo after sending? Double-tap Esc to edit and re-submit instead of sending a correction message that adds more context noise.
